## Прототип интеллектуальной системы обнаружения аномалий в корпоративной сети

Программа является прототипом аналитической системы, предназначенной для загрузки журналов событий и сетевой телеметрии, нормализации разнородных данных, формирования окон анализа, выявления аномалий, оценки риска и подготовки карточек выявленных аномалий для администратора.

Система не заменяет SIEM, IDS/IPS, NTA/NDR или средства мониторинга. Она используется как дополнительный аналитический слой поверх уже выгруженных файлов журналов и телеметрии.

```text
Журналы событий и сетевая телеметрия
        ↓
Импорт и определение формата
        ↓
Нормализация событий
        ↓
Агрегация в окна анализа
        ↓
Расчет признаков поведения
        ↓
Правила + ML-модель + показатель аномальности
        ↓
Карточки выявленных аномалий
        ↓
Риск + MITRE ATT&CK + рекомендации
```

---

## 1. Назначение

Прототип предназначен для:

- анализа журналов Windows, Linux и сетевой телеметрии;
- выявления аномалий в корпоративной сети;
- проверки событий из выгрузок SIEM, IDS/IPS, firewall, NTA/NDR, Zabbix и других источников;
- формирования карточек выявленных аномалий;
- оценки риска и приоритизации реакции администратора;
- расчета метрик качества на размеченных датасетах;
- демонстрации результата в рамках выпускной квалификационной работы.

Программа работает в режиме ретроспективного анализа: пользователь загружает файлы журналов, настраивает параметры анализа и запускает проверку вручную.

---

## 2. Основные возможности

- загрузка нескольких файлов одновременно;
- поддержка файлов без расширения;
- обработка Windows Event Log, Linux-логов и сетевой телеметрии;
- нормализация разнородных событий в единую структуру;
- формирование окон анализа;
- выявление известных и неизвестных аномалий;
- настраиваемые политики анализа через чек-боксы администратора;
- риск-ориентированная приоритизация;
- карточки выявленных аномалий;
- рекомендации по первичной проверке;
- сопоставление с MITRE ATT&CK;
- экспорт таблиц и карточек в CSV;
- расчет Precision, Recall, F1, ROC-AUC и матрицы ошибок при наличии разметки.

## 3. Поддерживаемые источники данных

### 3.1. Журналы событий узлов

| Источник | Примеры форматов | Для чего используется |
|---|---|---|
| Windows Event Log | `.evtx`, `.xml`, `.csv` | входы, ошибки аутентификации, службы, процессы, WFP-события |
| Sysmon | `.evtx`, `.xml`, `.json`, `.csv` | процессы, сетевые соединения, DNS-запросы, файлы |
| Linux auth/syslog | `.log`, `.txt`, файлы без расширения | SSH-входы, ошибки входа, системные сообщения |
| auditd | `audit.log`, `.log`, `.txt` | запуск процессов, сетевые соединения, доступ к файлам |

### 3.2. Сетевая телеметрия

| Источник | Примеры форматов | Для чего используется |
|---|---|---|
| Firewall / pfSense | `.log`, `.csv`, файлы без расширения | блокировки, разрешения, сканирование, флуд |
| IDS/IPS / Suricata / Snort | `.json`, `.log`, `.csv` | сигнатуры атак, алерты, сетевые события |
| SIEM-выгрузки | `.csv`, `.json`, `.cef`, `.leef` | нормализованные события безопасности |
| NTA/NDR / NetFlow / IPFIX | `.csv`, `.tsv`, `.json` | сетевые потоки, объемы, направления |
| Zeek | `.log`, `.tsv`, `.json` | DNS, HTTP, соединения, TLS |
| Proxy / Reverse proxy | `.log`, `.w3c`, `.csv` | HTTP-запросы, URI, ошибки, user-agent |
| DNS logs | `.log`, `.csv`, `.json` | DNS tunneling, DGA, NXDOMAIN, TXT-запросы |
| Zabbix | `.csv`, `.xlsx`, `.json` | метрики узлов, трафик, CPU, RAM, доступность |

## 4. Поддерживаемые расширения

Базово поддерживаются:

```text
.csv, .tsv, .json, .jsonl, .ndjson, .log, .txt, .evtx,
.xml, .w3c, .cef, .leef, .xlsx, .zip, .gz, .tar.gz,
.pcap, .pcapng
```

Файлы без расширения также могут быть обработаны, если программа определит их структуру по содержимому.

Архивы рассматриваются как контейнеры: программа извлекает содержимое и далее анализирует вложенные файлы.

## 5. Детектируемые классы аномалий

| Класс | Русское название | Возможные сценарии |
|---|---|---|
| `scan` | Сканирование | разведка сети, перебор портов, поиск открытых сервисов |
| `bruteforce` | Подбор учетных данных | brute-force, password spraying, ошибки SSH/RDP/SMB/VPN |
| `flood` | DDoS/флуд-активность | SYN/UDP/ICMP/HTTP flood, резкий рост соединений |
| `web_attack` | Подозрительная активность веб-сервиса | SQLi, XSS, path traversal, webshell, web probing |
| `suspicious_outbound` | Подозрительная исходящая активность | reverse shell, внешний канал, нетипичный исходящий трафик |
| `dns_anomaly` | DNS-аномалия | DNS tunneling, DGA, всплеск TXT/NXDOMAIN |
| `malware_beaconing` | Признаки командного канала | C2-маяки, регулярные малые соединения |
| `lateral_movement` | Латеральное перемещение | SMB/RDP/SSH/WinRM, обращение к внутренним админ-сервисам |
| `data_exfiltration` | Подозрительный вывод данных | крупная выгрузка, архивирование, массовое чтение файлов |
| `audit_tampering` | Изменение или очистка аудита | очистка журнала, изменение политики аудита |
| `account_change` | Изменение учетных записей | создание, удаление, включение, сброс пароля |
| `privilege_change` | Изменение привилегий | добавление в административные группы |
| `persistence` | Создание службы или закрепление | новая служба, возможное закрепление |
| `privileged_logon` | Привилегированный вход | вход с особыми правами |
| `suspicious_process` | Подозрительный запуск процесса | PowerShell, cmd, bash, curl, certutil, mshta и др. |
| `unknown_anomaly` | Неизвестная аномалия | высокий показатель аномальности без точного класса |

Результат системы является аналитическим заключением. Обнаруженная аномалия не является автоматическим доказательством атаки и требует проверки администратором.

## 8. Установка и запуск

### 8.1. Клонирование проекта

```bash
git clone https://github.com/ShevelevVladimir/Anomaly_log_detector.git
cd Anomaly_log_detector
```

### 8.2. Создание виртуального окружения

Windows:

```powershell
python -m venv .venv
.venv\Scripts\activate
```

Linux:

```bash
python3 -m venv .venv
source .venv/bin/activate
```

### 8.3. Установка зависимостей

```bash
pip install -r requirements.txt
```

### 8.4. Запуск приложения

```bash
streamlit run app.py
```

После запуска откроется веб-интерфейс Streamlit.

## 10. Порядок работы

1. Открыть вкладку **Инструкция** и ознакомиться с порядком анализа.
2. Загрузить один или несколько файлов журналов.
3. Настроить период анализа и размер окна агрегации.
4. Выбрать политики анализа в боковой панели.
5. Нажать кнопку **Запустить анализ**.
6. Перейти на вкладку **Обзор** для общей сводки.
7. Перейти на вкладку **Аномалии** для просмотра карточек.
8. При необходимости выгрузить выбранную карточку или все аномалии в CSV.
9. При наличии `true_label` посмотреть метрики во вкладке **Разработчик**.
10. Сформировать итоговый отчет во вкладке **Отчет**.

## 11. Окна анализа

Программа анализирует не каждую строку лога отдельно, а агрегирует события во временные окна.

Пример:

```text
286 000 исходных записей
        ↓
окно агрегации 5 минут
        ↓
примерно 4 000–5 000 окон анализа
```

Окно анализа — это временной интервал, по которому рассчитываются признаки: количество событий, число уникальных портов, число адресов назначения, объем трафика, ошибки входа, DNS-запросы и другие показатели.

Чем меньше окно агрегации, тем больше окон анализа и тем выше нагрузка на интерфейс.

Для больших файлов рекомендуется начинать с окна 5 минут.

## 12. Метрики качества

Если в загруженном датасете есть эталонная колонка `Label`, `label`, `true_label` или аналогичная разметка, программа может рассчитать:

- Precision;
- Recall;
- F1-score;
- ROC-AUC;
- матрицу ошибок;
- TP / FP / FN / TN.

Если эталонной разметки нет, программа выполняет функциональный анализ и формирует заключение, но объективные метрики качества не рассчитываются.

Для реальных журналов предприятия обычно используется функциональная проверка:

```text
загрузка логов → нормализация → окна анализа → выявленные аномалии → риск → рекомендации
```

Программа позволяет выгружать:

- таблицу всех выявленных аномалий;

## 14. Рекомендации для опытной проверки на предприятии

Для безопасной проверки в действующей сети рекомендуется использовать щадящие сценарии:

- ограниченное сканирование одного согласованного узла;
- контролируемые неудачные попытки входа только на тестовой учетной записи;
- анализ выгрузки Zabbix за период штатной и аномальной активности;
- загрузка логов firewall, Windows Security, Linux auth.log, SIEM или IDS/IPS за точный период проверки.

Не рекомендуется выполнять:

- DDoS/DoS;
- сканирование всей подсети;
- подбор паролей реальных учетных записей;
- эксплуатацию уязвимостей;
- очистку журналов;
- изменение учетных записей или групп;
- создание служб на рабочих серверах.

## 15. Ограничения

Текущая версия является прототипом и имеет ограничения:

- не выполняет постоянный фоновый сбор логов;
- не является inline-IPS;
- не блокирует трафик;
- не заменяет SIEM, IDS/IPS или NDR;
- точность зависит от состава загруженных источников;
- часть классов требует соответствующих логов: например, DNS-аномалии требуют DNS-логов, brute-force требует auth-журналов, сканирование лучше определяется по firewall/IDS/NTA;
- метрики качества возможны только при наличии эталонной разметки;
- реальные журналы без `src_ip`/`dst_ip` могут отображаться с пустыми адресами, если таких полей нет в исходном источнике.
